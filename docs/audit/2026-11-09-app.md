## 1. What is actually on screen in the reported scene

The reported scene is the **embedded workspace chat** (`DirectChatPage(embedded: true, morphProgress: _morphProgress)`, `bottom_panel.dart:2052-2079`), not the standalone route (`app_router.dart:303`), so the hosted bar exists only after the panel is fully open.

The composer on screen is **the native hosted accessory bar**, and it is the *only* composer drawn in that mode:

- `direct_chat_page_body.dart:189-191` → `hostedBarShown = bottomMode == chat && _composerAccessoryShown && _composerAccessoryReady`
- `direct_chat_page_state.dart:773-775` (`_composerBarShown`) — same predicate.
- `direct_chat_page_body.dart:966` → `hidden: !hostedBarShown` to the bar widget.
- `direct_chat_page_body.dart:1112-1123` (`_hostedComposerSlot`): when `hosted` it returns `Stack(alignment: bottomCenter, children: [bar, if (!barShown) child])` — i.e. **when the bar is shown the in-app composer is not in the tree at all**, and when the bar is hidden the in-app composer is stacked over the (still reserving) bar. The swap is meant to be invisible because both are the same `DuoChatComposer` (`chat_composer_accessory.dart:257-263` vs `:409-433`).

Switches between the two, complete list:

| condition | effect | where |
|---|---|---|
| `bottomMode != chat` (answer dock, score dock, authoring) | native bar **hidden**, in-app `ChatAnswerDock`/`ChatAuthoringDock` is the visible composer | body:179-185, 189-191, 949-1097 |
| panel progress `< .999` | `_composerAccessoryShown = false` → bar hidden, in-app composer rides the panel | state:104, 756-771, 642-652 |
| accessory engine not yet ready | `_composerAccessoryReady = false` → bar hidden, in-app copy shown | state:116-120, 779-782 |
| panel never fully opened this page | `_composerAccessoryMounted = false` → bar **not mounted at all** | state:106-111, 649-652 |
| `hideComposerUntilQuestionStateReady` (`!game.hasData || !messages.hasData`, and not editing) | whole composer slot + band item **unmounted** | body:148-149, 949 |

So: with a pending question living as a card in the feed (composer not owning it), `bottomMode == chat` and the composer the user sees and drags against is the **native bar**. If the composer had taken the round over (dock open, `_ownQuestion`), the visible composer would be the **in-app `ChatAnswerDock`** instead, and the bar would be hidden — a materially different failure path (see §4, bullet 3).

### Could frame B (composer invisible, keyboard open) be an app-side hide/swap?

Answer: **not by itself; only in combination with a wrong inset.** Evidence:

- Hiding the bar does not remove a composer: `_hostedComposerSlot` then paints the in-app copy at the bottom of the same reserved slot, which sits at the panel's bottom = keyboard top (as long as the inset is right). So a pure hide would show the Flutter composer, not an empty keyboard top.
- The only app change correlated with keyboard drag/release is none: no focus listener, no keyboard-notification listener, no `unfocus` on drag in the workspace (`grep FocusScope|unfocus` in `lib/view/workspace` → only `chat_settings_card.dart:210`; in `lib/view/chat/presentation` → only `direct_chat_user_picker.dart:43`). `didChangeMetrics` (`state:716-722`) only schedules a scroll-to-end.
- A **controlled** app hide *is* reachable but not from keyboard input: `bottomMode` comes from question/round/editing state (body:148-203), and `_composerAccessoryShown` only from `morphProgress` (state:746-771). Both are stable during a keyboard drag.
- Therefore frame B's most economical explanation is the native bar's own geometry: the bar (bottom == `keyboardLayoutGuide.topAnchor`, `CupertinoInteractiveKeyboardPlugin.swift:223`) laid out at the view bottom behind a still-open keyboard. Confidence: **high** that it is not a plain `hidden` flip; **medium** on the exact plugin mechanism (plugin agents own that).

One app-side alternate worth knowing, unrelated to drag: `_ExpandedChatState` wraps the page in `Visibility(visible: constraints.maxHeight >= 112, maintainState: true)` (`bottom_panel.dart:2091-2097`). If the keyboard inset ever exceeds the panel's content height (> panel − 112), the *whole chat* stops painting in one frame. Not plausible at `.85` extent on a phone (`.85*852 ≈ 724` vs keyboard ~290-340), so **low**.

## 2. What the app's layout does when `viewInsets.bottom` jumps — and why the list "jumps weirdly"

The chain, top to bottom:

1. `bottom_panel.dart:1076`: `bottomInset = MediaQuery.viewInsetsOf(context).bottom` — read by the panel's `build`, so every engine inset write rebuilds the panel subtree.
2. `bottom_panel.dart:1420-1440`: `AnimatedPadding(duration: defaultTargetPlatform == iOS ? Duration.zero : 180ms, padding: EdgeInsets.only(bottom: bottomInset))` wraps *the entire chat*. On iOS the app deliberately applies **no** easing ("iOS keyboard insets are animated per frame by the engine"). ⇒ **the app's chat surface is a 1:1 mirror of the engine inset, in one layout pass.** There is no interpolation, threshold, or clamp anywhere between the plugin's write and the pixels.
3. The chat body is `Column[Expanded(CupertinoInteractiveKeyboard(BottomOverlapViewport(ListView.reverse))), LayoutSizeProbe(band)]` (`body:205-1100`). Shrinking the child box by Δ moves the reversed list's bottom edge (scroll offset 0 = newest message) up/down by Δ in the same frame.

Consequences, quantified:

- **List: one-frame translation of Δ = the inset delta.** A standard iPhone keyboard is ~291-336 pt logical, so an inset write that jumps from "at the bar" to 0 (or vice versa) moves the whole visible feed by up to ~300 pt — roughly the entire visible list area at `.85` extent. That is the reported "list weirdly jumps". Confidence **high**; magnitude medium-high (exact Δ is whatever the plugin writes on release).
- **Second, slower motion after it:** `didChangeMetrics` fires on every inset change; if `position.pixels <= 96` it schedules `animateTo(minScrollExtent)` after **90 ms**, duration **280 ms**, `easeOutCubic` (`state:716-722`; `question_flight.dart:92-104`; constants `state:5-6`). The timer is restarted by each metric notification, so it fires once at rest: a 0-96 pt eased slide right after the release. This is what makes the motion read as "jump then weird slide" rather than one clean jump. Confidence **high** (code path), magnitude medium.
- **Composer/band heights are published by layout, and the list padding follows one frame late.** `LayoutSizeProbe` on the band → `_publishBottomBandHeight` / `_publishComposerHeight` (`body:822-823, 950-952`; `state:302-326`), and `_rebuildForBottomBand` schedules a `setState` in a **post-frame callback** ⇒ list padding updates on the *next* frame. `_listBottomPadding = 16 + _composerHeight/2` (`state:213-223`). So any composer-height change is a one-frame padding misfit.
- **The composer's reserved height changes with the bottom safe area.** When the bar is hosted, `_composerHeight` is the accessory reservation: `SizedBox(height: _reportedHeight ?? height + MediaQuery.padding.bottom)` in `cik/lib/src/cupertino_hosted_input_accessory.dart:126-135`, where `_reportedHeight` is the **bar total incl. the bar's bottom safe area** (`cik/.../CIKHostedAccessoryBar.swift:44-50, 87-103`). Keyboard open → bar safe area 0 → reserved ≈ 52; keyboard closed → bar safe area 34 → reserved ≈ 86 (`_reportedHeight = null` is re-armed on every `height` change, `:97-115`). Δ = 34 → `_listBottomPadding` steps by **17 pt** and the band probe re-publishes. Frame-late, and it happens on the same release. Confidence **high**; magnitude small (17 pt) but it is a second visible tick.
- **App-local animations do not cover the inset**, they only soften the band's own size changes: `AnimatedSize` 220 ms for the typing row (`body:835-846`), `AnimatedSwitcher` 250 ms for the partner pill (`body:849-918`), `_AnimatedComposerSwap` 240 ms (`body:1140-1194`), `_ComposerBandSlot` `AnimatedSize` `AppDurations.pinnedRowSwap` (`body:1207-1223`). `BottomOverlapViewport` reads overlap/clip at layout/paint only (`lib/ui/widgets/layout/bottom_overlap_viewport.dart:33-50`) — no animation. Fade masks (`_fadeBandLength`, `state:255-275`) are recomputed from the same measured numbers, so they jump with them.

**Verdict for Q2:** the "weird jump" is ~a 1:1 consequence of the plugin's inset write being discontinuous (up to ~300 pt, instant), plus the app's own 280 ms scroll-to-end ease and the one-frame-late 17 pt padding tick layered on top. It is **not** an app-made animation of the keyboard.

## 3. Does the app rebuild/remount the bar or toggle `hidden` on focus/keyboard/question changes?

Remount (`CupertinoKeyboardAccessory.dispose()` → `removeHostedAccessory()`, `cik/lib/src/cupertino_hosted_input_accessory.dart:117-124`; a remount creates a new accessory engine and re-reports its height):

- `hosted` flips false ⇒ `_hostedComposerSlot` returns `child` only ⇒ bar unmounted (body:1112-1123). `hosted = _composerAccessoryMounted`, which is **monotonic after the first full panel open** (state:756-771), so normally it never flips back. Triggers where it is still false: page first built with the panel not at `.999` (state:642-652), and `didUpdateWidget` replacing `morphProgress` only re-reads visibility, not the bar (state:1187-1193).
- `hideComposerUntilQuestionStateReady` becoming true unmounts the whole slot ⇒ bar remounted when it becomes false again. It is `!(gameSnapshot.hasData && messageSnapshot.hasData) && _editingMessage == null` (body:148-149, 88; data flags `direct_chat_page_scaffold.dart:53-61`). Since both StreamBuilders carry `initialData` from cache, this is normally true only on a cold, cache-less start; a stream that emits an error (or `_retryMessages`, state:909-915) can make `hasData` false mid-session and drop the bar + engine. **Medium** confidence this is ever hits the reported scene; it would look like a one-frame composer/reserved-band loss.
- Chat switch / page teardown: `_ExpandedChatState` caches the page per chat and keys it by `chatId` (`bottom_panel.dart:2038-2090`), so a new conversation remounts everything (expected).

`hidden` flag toggles (no remount, but it changes the plugin's band driver — see §4):

- `_syncComposerAccessory` (`state:756-771`) is the only writer, called from `_onSurfaceProgress` (`state:746-748`), which listens to `morphProgress` (`state:641, 1189-1192`).
- `_composerAccessoryReady` is set once from the engine's `ready` event (`state:779-782`, `chat_composer_accessory.dart:152-158`).
- Therefore `hidden` changes **only** with panel travel or the first ready frame. **No focus, keyboard, drag or pending-question trigger exists.** Confidence **high** (exhaustive: `hidden:` appears once, body:966; `_composerBarShown` has one caller, body:189).

## 4. The contract the plugin must provide for this app

The app has **no independent keyboard geometry**. Every pixel of the chat's vertical alignment comes from `viewInsets.bottom` (one reader: `bottom_panel.dart:1076`), and it applies it with **zero duration on iOS**. Therefore:

1. **Continuous, per-frame inset.** `viewInsets.bottom` must move with the keyboard on every frame of open, drag, release/cancel and close. A single discontinuous write moves the app's whole chat 1:1 (up to ~300 pt) and is unrecoverable app-side without adding an animation the app explicitly avoided. On release, the inset must either keep being written per frame or be handed to the engine's own animation *starting from the value the plugin last wrote* — never snapped to the end/final value at release.
2. **The inset must not be derived from the bar's own (possibly wrong) rect without a fallback.** The app is a mirror, so any error in `syncInset()`'s band rect (`cik/.../KeyboardManager.swift:229-276`, which reads the hosted bar's `liveScreenRect`) *is* a viewport error: a bar rect that lands at the view bottom reads as inset ≈ 0 ⇒ the app's padding drops to 0 in the same release frame ⇒ list drops behind the keyboard. Fixes must make the release path structurally unable to publish a "bar at the view bottom while the keyboard is open" reading (or cross-check against the keyboard notification's target inset before publishing). Confidence **high** on the coupling; **medium** on which guard is cheapest.
3. **A hidden bar must keep the driver alive.** App side, the bar is hidden exactly when the app *cannot* see it: `bottomMode != chat` (answer/score/authoring docks), panel travel, pre-ready. In those modes the app's composer is the in-app Flutter one, positioned **solely** by the inset. But the plugin drops the band view on hide — `CupertinoInteractiveKeyboardPlugin.swift:321-323`: `hostedAccessoryBar = hidden ? nil : bar` ("a hidden bar is not the live keyboard band") — and `startTrackingIfKeyboardVisible` requires `hostedAccessoryBar != nil` (`KeyboardManager.swift:114-133`). Net effect: **the one mode where the app depends only on the inset is the mode where drag tracking is disabled**, so the engine's own notification animation (or nothing) takes over. Confidence **high** (code read). Contract: either keep following the hidden bar's frame for the band, or expose a "hidden but still the band driver" mode.
4. **Reported reserved height must keep matching the bar's real height including the bar's bottom safe area, and must not step on keyboard open/close.** The app uses the reported value as `_composerHeight` → list padding = `16 + h/2` → 17 pt step today (`cik/.../CIKHostedAccessoryBar.swift:44-50, 87-103` → `cupertino_hosted_input_accessory.dart:151-161` → `state:310-326`). Contract: report a stable total (or make the safe-area component invariant, e.g. bar pinned above the keyboard carries no safe area) so the list padding does not tick when the keyboard settles.
5. **The bar must stay glued through open/drag/release and cancel.** `bottom == keyboardLayoutGuide.topAnchor` (`CupertinoInteractiveKeyboardPlugin.swift:223`) must hold during the interactive dismissal and its cancel **and** while the keyboard is still on screen after a release. Frame B says it does not. Confidence **high** that this is the observed composer disappearance.
6. **Bar width spans the Flutter view** (the app reserves a full-width band; the inset math assumes the bar spans the view, `KeyboardManager.swift:250-257` only guards the non-hosted case).

App-side assumptions that constrain any fix:

- The app assumes `viewInsets.bottom` = distance from screen bottom to the composer band bottom, **in logical pixels**, already scaled correctly (plugin writes physical px via `updateViewportMetricsWithInset:`, `KeyboardManager.swift:283-299`; engine converts). Changing that unit convention breaks the app.
- The app assumes the bar is **alive while hidden** and reserves its height regardless (`cik/lib/src/cupertino_hosted_input_accessory.dart:56-62`) — it never unmounts it to hide it, and never reclaims the space. So the plugin may not require unmounting to stop drawing, and may not change the reservation while hidden.
- The app assumes the bar's rect is trustworthy as a *position* (it never reads it) but not as a *height* to be inferred by the app — it only consumes the reported total.
- The app assumes the inset is 0 when the keyboard is closed (panel padding 0 ⇒ composer at the screen bottom), so a non-zero floor would leave a permanent gap above the home indicator.
- The app assumes the bar is full width and inside the Flutter view; it never compensates for a floating/undocked keyboard (plugin's problem, and the hosted bar guard at `KeyboardManager.swift:250-257` is skipped for it).
- The app has **no** keyboard state listener, so it cannot recover from a bad inset: no app-side "fix it on release" hook exists today. Any recovery must live in the plugin.

## 5. Recommendation: plugin only; app change optional hardening

**Primary fix belongs in the plugin.** The app is already the right shape for per-frame keyboard tracking (zero-duration inset consumption, reserved band, no own animation); its only fault is that it trusts the plugin's inset absolutely. Concretely the plugin must (a) publish a continuous inset through the release/cancel (never snap to the final band position), (b) not derive the release inset from a bar rect that can be at the view bottom while the keyboard is open, and (c) keep drag tracking alive for a hidden hosted bar. Cost: small, localized — `KeyboardManager.swift` (`syncInset` release guard + `liveScreenRect` fallback), `CupertinoInteractiveKeyboardPlugin.swift:321-323` (hidden band policy). No app release needed. Confidence **high** that this is sufficient for the reported symptoms.

**App changes are optional hardening, not required, and should not ship in the same breath** (they would mask a plugin bug):

1. Make the reserved composer height immune to the bar's safe-area step so the list padding does not tick 17 pt on keyboard settle. Cost: small app patch (`chat_composer_accessory.dart` `_contentHeight` vs total), touches the composer band; medium risk of drift between the bar and the in-app copy.
2. Avoid the 90 ms + 280 ms scroll-to-end when the change was only a metrics (inset) change (`state:716-722`). It is arguably correct behaviour (stay at the newest message while the keyboard moves), so I would leave it unless it is proven to contribute visibly. Cost: one condition; low value.
3. Do **not** add an inset animation in `bottom_panel.dart` as the fix. It would hide plugin discontinuities behind a 180-260 ms ease at the cost of the composer trailing the keyboard — exactly the trade the current zero-duration comment (`bottom_panel.dart:1422-1429`) rejects.

**What to verify before accepting a plugin fix**, from the app side: on a real device, log `MediaQuery.viewInsetsOf(context).bottom` once per frame (or the engine's inset writes) across drag → release → cancel. The expected trace is a monotone-ish sequence with no single-frame delta larger than the keyboard's per-frame travel (≲ ~15 pt). A single jump of 100-300 pt in that trace is the bug, and it is also exactly the list's displacement. Confidence **high** that this trace discriminates "plugin discontinuity" from "app swap" definitively.
