# UIKit audit — `keyboardLayoutGuide` through an interactive keyboard dismissal, and how to keep the hosted bar glued

**Scope** (task-2): how `UIView.keyboardLayoutGuide` behaves through an interactive keyboard dismissal
(drag + release) on iOS 15-18, whether it can be blamed for "hosted composer at the screen bottom while the
keyboard is open/animating", and ranked ways to keep `CIKHostedAccessoryBar` glued.

**Method**: read-only. Plugin sources under
`ios/cupertino_interactive_keyboard/Sources/cupertino_interactive_keyboard/`, Dart side `lib/src/`, the local
iOS SDK headers (`iPhoneOS27.0.sdk`), the exact-flavour Flutter engine sources
(`/Users/vitekvitek/development/flutter/engine/src/flutter`, deb287481e), Apple's published docs, and two
independent OSS/community implementations that solve this exact problem (react-native-keyboard-controller,
and the UIKit approach used by the ChatGPT iOS app as described by its author). No device was available; every
claim below is tagged with a confidence and with what would settle it.

---

## 0. TL;DR

1. **The guide is documented to follow the keyboard "while it is docked" — nothing more.** It is a
   `UILayoutGuide`, not a view, and UIKit never documents anything about its *interactive-dismissal* behaviour
   or its *release animation*. Local header: `iPhoneOS27.0.sdk/.../UIKit.framework/Headers/UIKeyboardLayoutGuide.h:17-34`.
   → depending on the guide for frame-accurate *release* motion is depending on undocumented behaviour.
2. **The guide does track the drag frame-by-frame** (two independent implementations read a guide-pinned
   view's frame/centre KVO per drag frame). So the plugin's *drag* looking right is expected.
3. **The guide never provides the release animation.** The two implementations above both stop reading the
   guide once the keyboard animates and animate the layout themselves; and there is a live bug report that the
   guide "is not animating back when the keyboard gets hidden" (RNKC #1591 / commit 769bf60, iOS 26.5).
4. **So yes: the guide can be blamed** — but the most consistent mechanism for the reported frames is *the
   guide is updated once to its **final** position at the release, with no animation* (the bar = pure Auto
   Layout follower of `guide.topAnchor` therefore snaps), **not** "the guide is left at the *release*
   position". The "left stuck at its last position" variant (RNKC #1591) is the second candidate and produces
   the same category of visible failure and the same fix.
5. **Independent second contributor found**: the bar's height = `content + bar.safeAreaInsets.bottom`
   (`CIKHostedAccessoryBar.swift:45-50,87-103`, `KeyboardGeometry.swift:33-38`) flips by the home-indicator
   inset (34 pt) *mid-drag* — when the bar crosses the bottom safe-area boundary — and the Dart side reserves
   that height as a `SizedBox` (`lib/src/cupertino_hosted_input_accessory.dart:131-135`), so the app layout
   jumps 34 pt in one frame. This is a real "the list weirdly jumps" contributor, independent of the release.
6. **Also found**: on iOS 15/16 `usesBottomSafeArea` does not exist (iOS 17+,
   `UIKeyboardLayoutGuide.h:30-31`), so the guide rests on the *safe area* bottom — the bar rests 34 pt above
   the screen bottom. The comment at `CupertinoInteractiveKeyboardPlugin.swift:225-230` ("on iOS 15/16 the
   guide already rests on the bottom edge") is **wrong**, and on those versions the plugin's band formula
   (`inset = viewBottom - bandBottom`, `KeyboardGeometry.swift:18-20`) reports a permanent 34 pt inset at rest.

## 1. What Apple actually documents (sourced)

### 1.1 The guide's contract, in Apple's words

**Conclusion (high confidence):** Apple documents (a) *what the guide represents*, (b) *where it rests when the
keyboard is off screen*, and (c) *that it "matches keyboard animations like bring up and dismiss"*. Apple
documents **nothing** about (d) how the guide updates during an interactive keyboard dismissal, (e) what its
constraint state is at the moment the pan is released, or (f) whether the release is animated. There is no
public API to force it to re-sync, no completion callback, and no way to observe its animation.

### 1.2 What is *not* in the docs but is observed

* **The guide is live during the drag.** react-native-keyboard-controller (RNKC) implements exactly the
  construct under audit: a 0-height `UIView` pinned `bottom == topView.keyboardLayoutGuide.topAnchor` (plus
  `usesBottomSafeArea = false` on iOS 17+), and reads the live keyboard position by **KVO on that view's
  `center`** (`ios/observers/movement/KeyboardTrackingView.swift`, `attachToTopmostView` /
  `interactive(point:)`; `ios/observers/movement/observer/KeyboardMovementObserver+Interactive.swift`,
  `setupKVObserver` → `keyboardDidMoveInteractively`). Their code comment on that path: *"for
  `keyboardLayoutGuide` case we can just read keyboard position directly - no interpolation needed"*.
  The same construct is described for the ChatGPT iOS app by its author: *"we constrain an empty view to the
  keyboard layout guide and … get live updates in the viewWillLayoutSubviews of the UIVCRepresentable **while
  the user is scrolling to dismiss the KB**"* (mastodon thread: <https://mastodon.social/@kylebshr/113321188106423439>,
  ancestors include the full exchange). Same thread, the other developer: *"layoutSubviews is only getting
  called with the initial and final values"* — i.e. for the *animated* show/hide the guide gives you endpoints,
  not interpolation.
  → **the plugin's correctly-following drag is not evidence that the guide handles the release.**

* **The guide does not animate the release.** RNKC ships a fix (commit
  <https://github.com/kirillzyusko/react-native-keyboard-controller/commit/769bf60>, 2026-08-12, "fix: stale
  `keyboardLayoutGuide` causes stuck subsequent animations (#1598)", closes
  [#1591](https://github.com/kirillzyusko/react-native-keyboard-controller/issues/1591)) whose motivation is
  literally: *"`keyboardLayoutGuide` is not animating back when keyboard gets hidden … we update
  `prevKeyboardPosition` every frame, but since view is stuck after animation completion then subsequent
  initialization will initialize the animation from final to final value (i. e. from 335 to 335)"*. Tested on
  iPhone 17 Pro / iOS 26.5. The workaround is to stop trusting their own tracked position and reset it in
  `keyboardDidHide` (`KeyboardMovementObserver+Listeners.swift`). More importantly, **RNKC never lets the
  guide own any animation**: on `keyboardWillShow`/`keyboardWillHide` they switch *off* the guide-KVO and
  switch *on* a `CADisplayLink` that interpolates their own animation model
  (`KeyboardMovementObserver+Animation.swift`, `+Watcher.swift`: they read the keyboard view's
  `layer.presentation()?.animation(forKey: "position")`, copy the `CASpringAnimation`/`CABasicAnimation`
  parameters, and evaluate the curve per frame). And they only use guide-based tracking at all on **iOS 26+**
  (`ios/core/KeyboardControllerConfiguration.swift`: `usesKeyboardLayoutGuideTracking` returns true only
  `#available(iOS 26.0, *)`); on iOS 15-25 they KVO the keyboard's own view instead
  (`KeyboardTrackingView.view` → `KeyboardViewLocator.shared.resolve()`).

* **Two UIKit limitations of the guide worth knowing for this plugin**: the guide does not work when the
  keyboard belongs to another app's window (iMessage app extension: [SO 56843448](https://stackoverflow.com/questions/56843448/keyboardlayoutguide-does-not-work-in-imessage-app));
  and the "guide + bar" pattern needs `usesBottomSafeArea = false` to reach the screen bottom, which only
  exists on iOS 17+ ([SO 73806830](https://stackoverflow.com/questions/73806830/how-to-ignore-the-safe-area-when-using-keyboardlayoutguide),
  accepted answer).

* **The guide's release update is a *layout* update, not an animation.** The plugin relies on this being free:
  `bar.bottomAnchor == flutterView.keyboardLayoutGuide.topAnchor`
  (`CupertinoInteractiveKeyboardPlugin.swift:218-224`) is the *only* thing positioning the bar; nothing else
  writes its frame. Whatever the guide's model position becomes at release, the bar's frame becomes in the same
  layout pass. If UIKit's release update is applied outside a `UIView` animation block (or with a zero
  duration), the bar *snaps* even though the keyboard window still has 200-300 ms of animation to run: Auto
  Layout cannot invent an animation the guide does not provide. During the drag the same mechanism is correct,
  because UIKit moves the keyboard without animation too.

### 1.3 Does the guide jump to its *resting* position, or stay at the *release* position?

Both are consistent with "the guide is not animating the release", and both are the same class of bug; they
differ in the final resting place and therefore in what the frames should show:

| Variant | What the frames would show | Support |
|---|---|---|
| **V1 — guide is updated once to the final position, unanimated** (release-dismiss: final = screen bottom; release-cancel: final = keyboard top) | composer *snaps* to where it must end, a few ms after the drag, while the keyboard is still animating. On a dismiss the composer appears at the screen bottom while the keyboard is still on screen mid-animation. | Matches the report's "the composer automatically **jumps** to the bottom **instead of animating with the keyboard**" and "they are a few ms apart" almost word for word. kylebshr/erichoracek (§1.2) show the guide gives endpoint values only. **Best fit — high confidence.** |
| **V2 — guide is left stale at the position it had when the gesture ended (or never reaches the new one)** | composer stays at the *release* position (mid-screen), hovering above the returning keyboard; the next keyboard transition starts from a wrong place. | Exactly what RNKC #1591 reports (view stuck at 335 while the keyboard hides). Produces the "composer behind/near the bottom while the keyboard is open" reading *only if* the user released close to the bottom, **or** if the stale value is the previously-committed *hidden* position (then the composer sits at the screen bottom while the keyboard is open). **Second best fit — medium confidence.** |
| V3 — guide jumps to the *hidden* position on a **cancelled** dismissal, then stays | composer at the screen bottom while the keyboard animates back up (and stays there) | Not separable from V2 with the evidence available; same fix. **Low-medium confidence.** |

**What I can state confidently:**

1. The guide is not a thing that can be "trusted to ride out a release". It exposes no animation contract, no
   API to re-sync, and at least one current OSS project had to stop trusting its post-release state on iOS 26.5.
2. Because the bar is a *pure constraint follower* of the guide, **the bar's release motion is exactly the
   guide's**, no matter which of V1-V3 is happening. It is therefore not necessary to distinguish them to fix
   the bug: in all three the plugin must stop using the guide as the bar's post-release authority.
3. I could **not** verify the release behaviour on iOS 15-18 from Apple documentation (none exists), and the
   community evidence I can cite is from iOS 17/26 devices. Treat "affected on iOS 15-18" as *assumed* (guide
   is undocumented there too) rather than proven. What is known per version: `usesBottomSafeArea` (iOS 17+)
   changes the resting geometry, and iOS 15/16 rest 34 pt above the view bottom (see §7).

## 2. Why this plugin's own drag works and its own release does not

The plugin has *two* independent position sources and uses each for a different thing:

* **the bar** (hosted accessory, second engine's view) → positioned **only** by
  `bottom == flutterView.keyboardLayoutGuide.topAnchor`
  (`CupertinoInteractiveKeyboardPlugin.swift:218-224`), height by a constant constraint
  (`CIKHostedAccessoryBar.swift:53,61-63,97-103`);
* **the Flutter viewport inset** (the *app's* Flutter content) → driven by `KeyboardManager.syncInset()`,
  which measures the bar's live rect and writes the inset through the private
  `updateViewportMetricsWithInset:` + `targetViewInsetBottom` (`KeyboardManager.swift:228-276,283-321`).

The inset path is protected against the guide's release: on the first engine-relevant notification the plugin
stops its own tracking and deliberately hands the release to the engine, *without reading the band again*
(`KeyboardManager.swift:86-89` + comment `:76-82`, and `docs/superpowers/specs/2026-11-09-keyboard-accessory-sync-design.md:34-35,74-80`).
The **bar** path has no equivalent: nothing hands the bar's release to anything, because "the guide moves it"
was the design assumption (`docs/superpowers/specs/2026-11-09-hosted-flutter-keyboard-accessory-design.md:18,43`,
`docs/research/2026-11-09-live-flutter-widget-in-native-keyboard-accessory.md:143`).

That asymmetry is the bug: the *list* is animated (by the engine) while the *composer* is snapped (by the
guide) — hence "a few ms apart", "instead of animating with the keyboard", and "the list weirdly jumps".

## 4. Ranked fix strategies

Ranked by (does it fix the visible symptom) × (size of diff) × (risk). "Cost" is implementation effort in
this repo, excluding device verification (~30-60 min per iteration, one drag + release recording).

### F1 — keep the guide for the drag, animate the bar's release yourself *(recommended first fix)*

**Mechanism**: in the same hook that already handles the release (`willProcessKeyboardNotification`,
`KeyboardManager.swift:86-89`) tell the bar to animate from its **presentation-layer position at that instant**
to its final position, with the notification's duration/curve. Two implementations:

* **F1a (smallest, safest): visual `transform.ty` correction.** The guide has already snapped the bar to the
  final position when the notification arrives; the bar's `layer.presentation()` still has the pre-jump
  position. Set `bar.transform.ty = releaseY - finalY` (instant, inside a
  `UIView.performWithoutAnimation` if needed) and animate it back to `.identity` with the keyboard's
  duration/curve. ~20-30 LOC in `CIKHostedAccessoryBar` + 3-5 LOC in `KeyboardManager`.
  Risk low (touches nothing on the drag path; no constraint surgery; `convert(_:to:)` on the bar already
  accounts for the transform, and the plugin has stopped reading the band at that point anyway).
* **F1b (cleaner, more code): own a bottom constraint constant.** Keep the guide constraint for the drag;
  on release, deactivate it, set `bottomConstraint.constant` to the final position minus the release position,
  animate to 0, re-activate at rest. ~50-70 LOC. Risk medium (two writers of one frame; one-frame constraint
  fights are easy to introduce).

**Which notification / which curve**: the release is delivered as
`keyboardWillChangeFrameNotification` with a real (non-zero) end frame, and a completed dismissal also posts
`keyboardWillHideNotification` (the plugin always stops tracking on WillHide, `KeyboardManager.swift:96-109`).
Take `keyboardAnimationDurationUserInfoKey` for the duration and `keyboardAnimationCurveUserInfoKey` for the
curve (`UIView.AnimationOptions(rawValue: UInt(curve) << 16)`; 7 = keyboard curve). **Caveat (medium
confidence)**: since iOS 15 the keyboard animation is a *spring* — the engine itself derives
`CASpringAnimation` stiffness/damping/mass from the animation it observes
(`FlutterKeyboardInsetManager.mm:331-347`), and the notification does not expose those parameters. A
`UIView.animate(withDuration:curve:)` will therefore be close but not identical; the faithful option is the
RNKC trick — copy the keyboard view's `layer.presentation()?.animation(forKey:"position")` and drive the bar
from it, or simply animate with the duration/curve and accept a slightly different feel. Cheap device probe:
log `UIView.inheritedAnimationDuration` inside the handler; if it is non-zero, UIKit is already inside its
animation block and the transform/constraint change will inherit the keyboard's curve for free.

**Also required**: keep the engine's target on the live inset before stopping tracking (already done,
`syncEngineTargetInset`, `KeyboardManager.swift:307-321`) so the composer and the list land together.

**Would I pick it?** Yes, as the immediate fix: smallest diff, only affects the broken path, easy to verify on
one recording, and it does not depend on which of V1-V3 is true (it makes the bar's motion the plugin's
business in all three).

### F2 — drive the bar from the plugin's existing live band (single source of truth) *(recommended follow-up)*

The plugin already owns a **frame-accurate** keyboard band: `CIKInputAccessoryView` returned as the text
input's `inputAccessoryView` (`FlutterTextInputView+Swizzle.swift:34-50`) with
`keyboardDismissMode = .interactiveWithAccessory` on `CIKScrollView` (`CIKScrollView.swift:16-23`). That is
the mechanism the classic path documents as riding "the keyboard frame for frame on open, interactive drag,
release and at rest" (`docs/superpowers/plans/2026-11-09-keyboard-accessory-sync.md:7`;
`docs/superpowers/specs/2026-11-09-keyboard-accessory-sync-design.md`), and it is independent of the guide.
But `syncInset` prefers the *hosted bar* over that band (`KeyboardManager.swift:238-244`) — i.e. in hosted mode
the plugin throws away the source it trusts and measures the thing whose position is suspect.

**Change**: on the display-link tick (the plugin already runs one, `KeyboardManager.swift:185-217`) and on
every `keyboardDragDidChange`, set the bar's bottom constraint from the accessory band's live position (the
band's screen rect, already computed by `liveScreenRect(of:in:)`, `KeyboardManager.swift:362-385`), and on
release animate the residual. Then the bar and the inset are computed from the *same* measurement, which also
removes the composer/list mismatch class entirely.
**Cost** ~80-120 LOC (one new writer of the bar's frame, plus deactivating the guide constraint in hosted
mode); **risk** medium-high (needs a device check that a 0-height accessory view is installed and moved by
`.interactiveWithAccessory` in hosted mode — the plugin's own `startTrackingIfKeyboardVisible`
(`KeyboardManager.swift:114-133`) already assumes it is on window, which is weak evidence that it is laid
out); **verifiability** high (same recording + a log of band vs guide vs bar).

### F3 — put the hosted bar into the text field's `inputAccessoryView` so UIKit owns it *(largest, most robust)*

This is the iMessage architecture: an input bar above the keyboard is only a first-class participant of the
interactive dismissal if it *is* the `inputAccessoryView` ([SO 79883939](https://stackoverflow.com/questions/79883939/) —
the asker's input bar does not participate in the drag precisely because it is a safe-area inset, not the
accessory). The plugin already swizzles the getter and already has the accessory-height bookkeeping
(`CIKInputAccessoryView`, `KeyboardManager.adjustKeyboardNotification`), and UIKit's release animation for an
accessory view is the keyboard's own — no guide involved.

**Change**: host the second engine's `FlutterViewController` view inside `CIKInputAccessoryView` instead of
`CIKHostedAccessoryBar`; drive its height through `intrinsicContentSize` + `reloadInputViews()`; delete the
guide pin, the bar's safe-area height arithmetic and (probably) the whole hosted-mode band special-casing;
the main engine's inset then needs the existing "subtract the accessory height from the notification frames"
adjustment that the classic path already uses (`KeyboardManager.swift:36-61`) — and that adjustment becomes
load-bearing again, including when the bar height changes.
**Cost** large (rewrite of the hosted path, ~200+ LOC net change, Dart side unchanged); **risk** high (a
Flutter engine's view inside the keyboard's accessory host, `reloadInputViews` churn on height changes, focus
and dismissal interactions, keyboard-extension/Stage Manager edge cases, and the accessory height now feeds
the main engine's inset); **payoff** the only design where the *release* motion is guaranteed by UIKit on every
iOS version, in both directions, with no private API. If the plugin's long-term goal is "the composer is the
keyboard accessory", this is where it should end up.

### F4 — notifications only (no guide) *(not sufficient alone)*

Animating the bar's constraint from `keyboardWillChangeFrame`/`keyboardWillHide` alone works for the release
and for show/hide, but **during the drag there are no usable notifications** (the frame changes posted while
dragging carry a zero/empty frame — the engine's own filter documents this,
`FlutterKeyboardInsetManager.mm:100-110`, and the plugin mirrors it, `KeyboardManager.swift:96-109`), so the
bar's live position has to come from somewhere: the guide (→ F1), the accessory band (→ F2), or the keyboard's
own view (RNKC's `KeyboardView.find()`/presentation-layer reading, which is private-hierarchy spelunking).
**Verdict**: not a standalone fix; it is the *release* half of F1/F2.

### F5 — other (cheap experiments worth running, not fixes)

* **`keyboardDismissPadding = barHeight` (iOS 17+, one line).** Documented for exactly this shape (a view above
  the keyboard, dismissal gesture starting above it) and it is what the WWDC23 sample does for a toolbar over
  the keyboard. It fixes *where the dismissal gesture starts*, not the release animation — but it is worth one
  line to see whether it also changes the guide's behaviour when the bar is a constraint participant. **No
  expectation that it fixes the jump.**
* **Re-create/re-anchor the bar at the release** (deactivate + re-activate the guide constraint inside an
  animation block, or `setNeedsLayout`+`layoutIfNeeded`): **does not recover it.** The guide is a layout
  guide, not a view; `setNeedsLayout`/`layoutIfNeeded` re-applies the guide's *current* model frame, and
  there is no public way to make UIKit re-derive it. If the guide is stale (V2/V3) you are re-applying the
  stale value; if it is final-but-unanimated (V1) you are re-applying the final value. Re-creating the bar has
  the same property (and adds a forced `layoutIfNeeded`, `CupertinoInteractiveKeyboardPlugin.swift:277`).
  *What does work*: animate the bar yourself (F1), or position it from a source UIKit animates (F2/F3).
* **Keep the guide pin but also clamp the bar** (e.g. `bar.bottomAnchor <= guide.topAnchor` plus a floor): a
  clamp can only pull the bar *up*; it cannot re-animate the release, and it turns a snap into a different
  snap. Not recommended.

**Pick**: F1a now (fix the visible jump, lowest risk), F2 next (remove the guide from the critical path for
*both* the bar and the inset), F3 if and when the hosted path is re-architected. F1a and F2 are additive and
compatible; F1a is also the fallback if F3 is rejected.

## 5. Safe-area handling (item 4 of the brief)

**Current**: `CIKHostedAccessoryBar.barHeight = contentHeight + safeAreaInsets.bottom`
(`CIKHostedAccessoryBar.swift:45-50`, `KeyboardGeometry.swift:33-38`), recomputed whenever
`safeAreaInsetsDidChange`/`layoutSubviews` fires, reported to Dart (`:232-234`,
`CupertinoInteractiveKeyboardPlugin.swift:144`), and reserved by a `SizedBox`
(`lib/src/cupertino_hosted_input_accessory.dart:131-135`).

**Is it right?** The *intent* is right (the bar must clear the home indicator when it rests at the screen
bottom, and must not add that padding when the keyboard covers it), but as a *live invariant* it is wrong:

1. the bar's own `safeAreaInsets.bottom` is a function of where the bar is, and during a drag the bar crosses
   the safe-area boundary, so **the bar's height and the Dart reserved height change in one frame mid-drag**
   (0 ↔ 34 pt). On top of that the change is a constraint write from `layoutSubviews`
   (`CIKHostedAccessoryBar.swift:92-103`), i.e. a second layout pass, not animated with anything;
2. on **iOS 15/16** the guide rests on `safeAreaLayoutGuide.bottom`
   (`UIKeyboardLayoutGuide.h:30-31`, `usesBottomSafeArea` is iOS 17+), so the bar rests 34 pt above the view
   bottom *and* the guide-pin comment in the plugin is contradicting the header
   (`CupertinoInteractiveKeyboardPlugin.swift:225-230`). The band formula then reports a 34 pt inset at rest
   (`KeyboardGeometry.inset`), so on those versions the list ends the dismissal with a 34 pt step;
3. the extra 34 pt is *above* the keyboard-top-pinned bar, so with the keyboard open the bar is 56 pt
   (correct) but at rest it is 90 pt with the composer's bottom 34 pt above the screen bottom — the composer
   content inside the accessory engine gets that as its own `MediaQuery.padding.bottom`, which is why the
   arithmetic "works"; it just should not be recomputed from the bar's own position mid-flight.

**Correct handling**: compute the padding from a value that does not move with the bar — the Flutter view's
(or window's) bottom safe area — and decide *when* it applies from the keyboard state, not from the bar's
position:

* `padding = keyboardVisible ? 0 : flutterView.safeAreaInsets.bottom` (and on iOS 15/16 additionally fix the
  resting guide offset: either stop using the guide for the resting position or subtract the safe-area bottom
  from the expected resting band);
* change `hostedAccessoryHeight(contentHeight:safeAreaBottom:)` to take `(contentHeight, keyboardVisible,
  windowSafeAreaBottom)` so the 34 pt only ever appears/disappears together with a keyboard transition, and
  animate that constraint change with the same duration/curve as the release;
* or keep the height constant and let the accessory engine apply the padding (it already sees its view's safe
  area) — but then the reserved height in the main isolate must be constant too, otherwise the app layout still
  steps.

**Does it contribute to the reported jump?** To "the list some weirdly jumps": **yes, plausibly 34 pt of it**
(a one-frame re-layout of the whole chat list, plus the composer's reserved slot changing size, exactly when
the bar crosses the home-indicator line). To "the composer jumps to the bottom while the keyboard is open":
**no** — that is the release/guide mechanism (§0.4, §1.3). It is a separate, independently fixable bug.

## 6. What would settle V1 vs V2/V3 on a device (3 log lines, no new dependency)

In `willProcessKeyboardNotification` (`KeyboardManager.swift:86-89`) and in
`CIKHostedAccessoryBar.layoutSubviews` (`:92-95`), log per sample:
`CACurrentMediaTime()`, notification name + `duration` + `curve` + end-frame `minY`,
`bar.frame` (in `flutterView`), `flutterView.keyboardLayoutGuide.layoutFrame`, and
`bar.layer.presentation()?.frame`. Then one drag-and-release:
* `guide.minY` moves to its **final** value in one sample while `presentation().frame.minY` still ramps, and
  `end.minY` differs from the final value → **V1** (guide jumped to final, keyboard still animating);
* `guide.minY` **stays** at the release value for the whole animation while `end.minY` reaches the keyboard
  top → **V2** (stale);
* `guide.minY` goes to the resting/hidden value and stays while `end.minY` is the keyboard-open top → **V3**.
This is the same instrumentation block proposed independently in `docs/audit/2026-11-09-engine.md` §8 (site N8);
it costs ~5 lines and discriminates all three.
