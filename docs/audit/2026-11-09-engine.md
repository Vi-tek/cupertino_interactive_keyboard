## 0. Brief corrections (facts that are wrong or misleading)

1. **`FlutterKeyboardManager.mm` has nothing to do with keyboard insets or keyboard notifications in this
   engine.** It routes hardware `UIPress`/key events to primary/secondary responders
   (`FlutterKeyboardManager.mm:53-110`). The keyboard *notification* observers live in
   `FlutterViewController.mm:394-407` and forward to `FlutterKeyboardInsetManager`
   (`FlutterViewController.mm:1542-1563`). Any reasoning based on `FlutterKeyboardManager` is void.
2. There is **no** animation-duration/curve stored by the engine beyond the notification's
   `UIKeyboardAnimationDurationUserInfoKey` (`FlutterKeyboardInsetManager.mm:54`); the curve is borrowed from
   UIKit's own implicit animation on the hidden tracking view (`FlutterKeyboardInsetManager.mm:287-303`).
3. `FlutterKeyboardInsetManager.targetViewInsetBottom` is `readonly` in the header
   (`FlutterKeyboardInsetManager.h:146`) and `readwrite` in the class extension
   (`FlutterKeyboardInsetManager.mm:20`). The plugin's `setValue:forKey:` therefore **works but only at
   runtime** — it depends on the class extension existing, exactly as the plugin assumes
   (`KeyboardManager.swift:307-321`). Verified: the setter is synthesized, and nothing observes the key
   (no KVO in the tree).
4. Consumer finding relevant to "the composer jumps": the visible composer during a dismissal is the
   **native bar** (`uptalk/lib/view/chat/presentation/direct_chat_page_body.dart:949-968,1112-1123`;
   the Flutter fallback composer is only mounted when `!barShown`, and `barShown` does not depend on the
   keyboard: `direct_chat_page_state.dart:774-775`). So "composer at screen bottom" cannot be produced by
   the engine inset — see §7 route N1.

## 1. Timeline

### 1a. The drag (finger down, keyboard follows)
* iOS posts `UIKeyboardWillChangeFrameNotification` with a **zero** `UIKeyboardFrameEndUserInfoKey` while the
  keyboard is dragged. The engine knows this and filters it out:
  `FlutterKeyboardInsetManager.mm:100-110`. So **the engine does nothing during the drag** — no animation,
  no inset write, `targetViewInsetBottom` untouched.
* The plugin mirrors that filter (`KeyboardManager.swift:96-109`) so its display-link tracking survives.
* The plugin writes `physical_view_inset_bottom` directly on every gesture change and every tick
  (`KeyboardManager.swift:140-156, 191-217, 229-276`) and mirrors each written value into the engine's
  `targetViewInsetBottom` (`KeyboardManager.swift:274, 307-321`).
* Consequence: while the plugin tracks, the engine's manager is a passive observer. Its only state change
  is the injected `targetViewInsetBottom`.

### 1b. Release-cancel (keyboard animates back up)
Real iOS notification sequence for the release (as far as the engine's own filters and the plugin's
comments describe it):
1. `UIKeyboardWillChangeFrameNotification` whose end frame is the released position →
   `calculateKeyboardInset` = the live inset, which **equals the plugin's injected target** → the engine
   **returns without animating** (`FlutterKeyboardInsetManager.mm:66-69`). The plugin's swizzled handler has
   already called `stopInteractiveTracking()` for this notification (`FlutterViewController+Swizzle.swift:19-35`
   → `KeyboardManager.swift:86-89,173-183`) — this is exactly the ordering the plugin's comment at
   `KeyboardManager.swift:73-85,301-306` describes.
2. `UIKeyboardWillChangeFrameNotification` (or `WillShowNotification`) with the docked frame, duration from
   UIKit (≈0.25 s, spring) → `calculatedInset` = full keyboard inset ≠ target → target updated
   (`:70`), direction computed from begin/end frames (`:77`), and because the plugin invalidated the vsync
   client on its first write (`KeyboardManager.swift:324-340`) `keyboardAnimationIsCompounding` is false
   (`:78-79`) → `startKeyBoardAnimation:duration` (`:249-315`).
3. `startKeyBoardAnimation` takes the animation's start value from
   `delegate.physicalViewInsetBottom` (`:273-276`) — i.e. the *last physical inset the plugin wrote*, which is
   the dragged position — and animates the hidden tracking view to `targetViewInsetBottom` over the
   notification's duration while a `FlutterVSyncClient` submits the presentation-layer position every vsync
   (`:282-314, 349-411`). **It animates, from the dragged position.**

### 1c. Release-complete (dismiss)
`WillChangeFrame` with an off-screen end frame, or `WillHideNotification`. `calculateKeyboardAttachMode`
returns `FlutterKeyboardModeHidden` for `WillHide` unconditionally (`:154-156`) and for a frame with no
intersection with the view (`:176-187`), so `calculatedInset == 0` (`:226-247`).
* If `targetViewInsetBottom != 0` → same animated path as 1b, from the live inset down to 0.
* **Special case** `keyboardMode == Hidden && calculatedInset == 0 && duration == 0` → `hideKeyboardImmediately`
  (`:56-64`): kills the vsync client, drops the animation view and the spring, sets
  `targetViewInsetBottom = 0`, and calls `ensureViewportMetricsIsCorrect` (`:317-329, 424-427`), which writes
  **one** metrics update — no animation at all. The engine's own test asserts this
  (`FlutterViewControllerTest.mm:960-1018`). This branch exists as a PasswordManager-prompt workaround
  (flutter/flutter#164884).

### 1d. Release at rest (no further movement)
If the released position already equals the resting inset, every following notification computes the same
inset and is dropped at `:66-69`. Nothing is written; the inset keeps whatever the plugin last wrote. See
§7 route E2 (sticky inset).

### 1e. Drag started while the show animation is still running
The plugin's first write calls `invalidateKeyboardAnimationVSyncClient` (`KeyboardManager.swift:324-340`).
Effect on the engine (`:413-416`): `_keyboardAnimationVSyncClient = nil`, the display link is invalidated on
the UI runner. The hidden view's `UIView` animation is **not** removed and `keyboardAnimationIsShowing`
stays `YES`; its completion block then no-ops because the identity check
`strongSelf.keyboardAnimationVSyncClient == currentVsyncClient` fails (`:304-313`). Net: no stray write, no
`ensureViewportMetricsIsCorrect`, and at release the compounding branch cannot be taken
(`:78-79` needs a non-nil client), so a fresh animation starts from the live inset. **This is correct
behaviour and it depends entirely on the plugin's invalidation.**

## 2. `updateViewportMetricsWithInset:` — semantics and conflicts

* Implementation: `FlutterViewController.mm:2312-2315` — writes
  `_viewportMetrics.physical_view_inset_bottom = inset` and calls `updateViewportMetricsIfNeeded`
  (`:1368-1375`), which forwards **the whole `_viewportMetrics` struct** to
  `[engine updateViewportMetrics:]` when `_shouldIgnoreViewportMetricsUpdatesDuringRotation` is false and
  `engine.viewController == self`.
* Chain: `FlutterEngine.mm:385-390` → `platformView->SetViewportMetrics(kFlutterImplicitViewId, …)` →
  `Shell::OnPlatformViewSetViewportMetrics` (`shell/common/shell.cc:1131-1160`) which runs the UI-thread
  part **synchronously** via `fml::TaskRunner::RunNowAndFlushMessages` (`:1154-1160`) →
  `Engine::SetViewportMetrics` → `runtime_controller_->SetViewportMetrics` + `ScheduleFrame()`
  (`shell/common/engine.cc:346-350`).
* **No throttling or coalescing anywhere in that path.** One call = one blocking platform→UI handoff + one
  scheduled frame. The plugin therefore schedules a frame per drag event and per display-link tick
  (`KeyboardManager.swift:140-156` is up to two writes per event; `:191-217` one per tick), on top of the
  frames the engine's own animation schedules. Cost, not correctness.
* **The inset is sticky.** `_viewportMetrics.physical_view_inset_bottom` is written in exactly one place in
  the whole iOS embedder — `FlutterViewController.mm:2313`. `setViewportMetricsSize` (`:1508-1522`) and
  `setViewportMetricsPaddings` (`:1527-1537`) do not touch it, and neither does `viewDidLayoutSubviews`
  (`:1377-1416`) or `viewSafeAreaInsetsDidChange` (`:1501-1505`). So a later layout pass **re-sends the
  last written inset** — it can neither revert it to 0 nor recompute it from the live keyboard. Answering the
  brief's question directly: a stale `_viewportMetrics` cannot *overwrite* the plugin's value; the real risk
  is the opposite — a **stale value that nothing corrects** (route E2).
* Conflicts: (a) during a rotation transition `updateViewportMetricsIfNeeded` silently drops writes while
  keeping them in `_viewportMetrics` — a drag that happens during that window is not delivered until the flag
  clears (`:1368-1372, 890-903`); (b) `hideKeyboardImmediately` writes 0 through the same path
  (`:327-328, 424-427`); (c) `viewDidDisappear` calls `hideKeyboardImmediately` (`:861`), so any engine inset
  is flushed to 0 when the VC disappears.
* `physicalViewInsetBottom` (`:2317-2319`) reads that same field, which is why the plugin's writes and the
  engine's animation start value agree.

## 3. Animation mechanics per release scenario

`startKeyBoardAnimation:` (`:249-315`): removes running animations (`:270`), seeds the hidden view's frame
from `physicalViewInsetBottom` (`:273-274`), records `originalViewInsetBottom` (`:276`), invalidates the old
client (`:279`), creates a client and `await`s it (`:282-284, 385-411`), then
`[UIView animateWithDuration:duration …]` to `targetViewInsetBottom` (`:287-303`). Per vsync the engine
reads the **presentation layer** (`:372-380`) or the spring curve (`:377-380`) and pushes it
(`:382`). On completion, if this is still the same vsync client, it invalidates, removes the tracking view
and writes `targetViewInsetBottom` once, unanimated (`:304-313 → 424-427`).

| Scenario | Animates? | From → to | Instant-jump path? |
|---|---|---|---|
| Drag | engine idle (`:100-110`) | plugin-driven | n/a |
| Release-cancel | **yes**, notification duration | last plugin inset → full | only if duration == 0 (§3a) |
| Release-complete, duration > 0 | **yes** | last plugin inset → 0 | only if duration == 0 (§3a) |
| Release-complete, `WillHide` duration == 0 | **no** | → 0 in one write | **yes** — `:56-64` → `:317-329` |
| Release at rest | no-op | unchanged | sticky value (E2) |
| Drag during show animation | **yes**, fresh animation | live inset → resting | no (plugin's invalidation defeats the compound branch) |

### 3a. Every path that yields an instant jump
1. **Duration 0 (generic).** `[UIView animateWithDuration:0 …]` runs the animation block and the completion
   immediately; completion is the same client, so `ensureViewportMetricsIsCorrect` writes the target at
   once (`:287-315, 312, 424-427`). The one vsync callback that may precede it only adds one intermediate
   value. Nothing in `:249-315` special-cases duration 0.
2. **`hideKeyboardImmediately` (`:317-329`)**, reached from the `Hidden + 0 + duration==0` test at `:56-64`
   (deliberate, PR #164884) and from `viewDidDisappear` (`FlutterViewController.mm:861`).
3. **Compounding branch with no spring** (`:78-88`): if the new notification has the same direction as the
   running animation, the engine only assigns `targetViewInsetBottom` (or `spring.toValue`) and never
   retargets the tracked `UIView` animation. If `keyboardSpringAnimation` is nil — which it is for
   `+[UIView animateWithDuration:animations:]`, the engine's own test only accepts a real
   `CASpringAnimation` (`FlutterViewControllerTest.mm:387-413`) — the inset follows the old curve to the
   **old** target and then snaps to the new one in the completion block (`:312`). The plugin's per-write
   invalidation makes this branch unreachable while it tracks; it is reachable if the plugin's
   `syncInset()` returned nil and never invalidated.
4. **Interrupted-animation completion ordering** (`:270` `removeAllAnimations` runs *before* the new client is
   established at `:282-285`): if UIKit delivers the interrupted animation's completion synchronously, the
   block sees the old client as current and writes the *already updated* new target unanimated
   (`:304-313`), and the new animation then starts at that value (zero travel ⇒ no animation). Low
   confidence on UIKit's timing, but the ordering invites it; the plugin's invalidation avoids it for its own
   releases.
5. `ensureViewportMetricsIsCorrect` (`:424-427`) is the only unanimated writer and it is called from the
   completion block of *every* animation (`:312`), so the last frame before a completion can be one animation
   step away from the final value — small, not the reported jump.

### 3b. Points vs pixels on `keyboardAnimationView`
`physicalViewInsetBottom` and `targetViewInsetBottom` are **physical pixels**
(`:226-247` multiplies by `screen.scale`; `:243-244`), yet they are written into a `UIView.frame` origin,
which is points (`:274, 296`), and read back as pixels (`:375, 382`). The mismatch cancels: the tracked path is
numerically in pixels end to end, so there is **no scale bug**; the hidden view simply sits at up to ~3× the
real keyboard travel (it is `hidden`, 0×0, and never hit-tested). The plugin's own writes use the same unit
(`KeyboardGeometry.swift:18-20` multiplies by `scale`), so plugin and engine agree. `SpringAnimation`
(`:331-347`) is fed the same pixel numbers, consistent again.

## 4. Swizzled ordering: what stopping first implies

`KeyboardManager.willProcessKeyboardNotification` runs **before** the original engine handler for all three
observers (`FlutterViewController+Swizzle.swift:19-35`). It stops the display link and clears
`lastReportedInset`/`lastBandBottom` (`KeyboardManager.swift:86-89, 173-183`) but deliberately does **not**
write the band (`KeyboardManager.swift:73-85`).

* Correct, and necessary: the engine reads its animation start value from
  `physicalViewInsetBottom` (`:273`), i.e. the plugin's last write. Stopping first means the engine owns the
  release; writing the band first would snap the content to the *resting* position and the animation would
  start at its own end value (`:66-69` would then also swallow the notification).
* The cost is bounded but real: the last plugin write can be up to one display-link tick + one main-queue turn
  old (`KeyboardManager.swift:140-156, 191-217`; the vsync callback itself is `dispatch_async` to main,
  `FlutterKeyboardInsetManager.mm:397-403`). The engine then animates from that slightly stale value — a
  few-millisecond-sized correction, matching "they are a few ms apart" but **not** a jump to the bottom.
* Not too early relative to UIKit: the notification for the release guarantees that UIKit has already fixed the
  frame it is going to animate to. Stopping *before* the engine also prevents the plugin's display link from
  overwriting the engine's first animated values mid-animation (otherwise the engine's own tick and the
  plugin's tick would fight through the same `updateViewportMetricsWithInset:` field).

## 6. `FlutterVSyncClient` / `SpringAnimation` and interactive-specific paths

* `FlutterVSyncClient` = `VSyncClient.swift` (Swift class bridged as `FlutterVSyncClient`). `await()`
  unpauses (`:112-114`), `allowPauseAfterVsync = NO` keeps it ticking (`FlutterKeyboardInsetManager.mm:409`,
  `VSyncClient.swift:198-201`), `invalidate()` nils the link and hops to the creating thread (`:130-145`).
  The display link is added **on the UI task runner's run loop** (`:72-75`), not the main run loop, and each
  tick is re-dispatched to the main queue with a one-frame projection
  (`FlutterKeyboardInsetManager.mm:397-403`). So inset writes land one main-queue turn after the vsync — they
  are *not* guaranteed to make the frame that is being prepared.
* `SpringAnimation` (`third_party/spring_animation`, fed from `FlutterKeyboardInsetManager.mm:331-347`) is
  only used when UIKit's own implicit animation on `position` happens to be a `CASpringAnimation`. For the
  `+animateWithDuration:animations:` call at `:287` it is a plain `CABasicAnimation` on real devices, so
  `_keyboardSpringAnimation` is nil and the presentation-layer path is authoritative (the engine's test
  encodes exactly this distinction, `FlutterViewControllerTest.mm:387-413`). This is also why the compound
  branch (`§3a.3`) degrades to "no retarget".
* Interactive-dismissal-specific code in the engine: **none** in the inset path. The only interactive-keyboard
  awareness is in `FlutterTextInputPlugin` for Flutter's own text field
  (`FlutterTextInputPlugin.mm:58-61,2641-2645`), and the engine's interactive-keyboard tests are disabled on
  iOS 17+ with *"broken on iOS 17+ due to SDK bugs"* (`FlutterTextInputPluginTest.mm:3617-3621`,
  flutter/flutter#183473). `hideKeyboardImmediately` callers are only `:62` and
  `FlutterViewController.mm:861`. `isKeyboardInOrTransitioningFromBackground` is set
  (`FlutterViewController.mm:1033,1055`) but **read by nothing** inside the engine — it is observability only
  (tests assert it).
* Hidden-view housekeeping: after the plugin invalidates the client mid-animation, the hidden tracking view
  stays in the hierarchy until the next `startKeyBoardAnimation` (`:259-267`) or `invalidate` (`:429-432`);
  it is `hidden` and 0×0, so no draw cost, but it is a leftover.

## 7. Ranked routes to the observed symptom

**E1 — (engine, list) `hideKeyboardImmediately` on a duration-0 `WillHide` while the keyboard is still on
screen.** `FlutterKeyboardInsetManager.mm:56-64,317-329`. One unanimated write of 0 ⇒ the Flutter list snaps
to full height and anything laid out against `viewInsets` lands at the bottom of the screen, at the exact
instant the keyboard is still mid-animation. Matches *"it will collapse by itself … it maybe sends some
notification and the composer automatically jumps to the bottom … instead of animating with the keyboard"*
and *"the list some weirdly jumps"*. Confidence **medium** (needs the notification's duration == 0, which was
not measured — see §8).

**E2 — (engine, list) sticky inset after an ignored notification.** `:66-69` + the single-writer field
(`FlutterViewController.mm:2313`). If the released position already equals the resting inset, the engine drops
every following notification and never re-derives the inset from the keyboard, so the content stays at the
dragged position until some later keyboard event animates it away — a "list is in the wrong place, then jumps"
signature. Confidence **medium-low** (requires the notification stream to stop after that point).

**E3 — (engine, list) unanimated release because the animation was interrupted or started at its own end
value** (§3a.3, §3a.4): only reachable when the plugin did not invalidate the vsync client or when a whole
animation completes inside one runloop turn. Confidence **low** for this repro.

**N1 — (non-engine, composer) `keyboardLayoutGuide` re-anchors at the release.** The bar is pure Auto Layout:
`bar.bottomAnchor == flutterView.keyboardLayoutGuide.topAnchor` + a fixed height constraint
(`CupertinoInteractiveKeyboardPlugin.swift:220-230`, `CIKHostedAccessoryBar.swift:53,61-63,97-103`). The
engine inset cannot move it, and the composer is the bar, not the Flutter fallback
(`direct_chat_page_body.dart:1112-1123`, `direct_chat_page_state.dart:774-775`). "Composer at the screen
bottom while the keyboard is still open" therefore means *the guide reported the resting position while the
keyboard was still on screen* — a UIKit behaviour of the dismissal (or an app-driven
`updateHostedAccessoryHidden`, `CupertinoInteractiveKeyboardPlugin.swift:321-324`). Confidence **medium**;
discriminated by the instrumentation in §8.
**This is the route the frames show**: two frames a few ms apart cannot be two steps of a 0.25 s animation, so
something wrote an end state in one frame. The engine's only one-frame writer is E1.

**N2 — (non-engine, composer) bar hidden/mounted state flap.** `updateHostedAccessoryHidden` sets
`isHidden` and stops the bar being the band (`CupertinoInteractiveKeyboardPlugin.swift:316-324`); if Dart
flips `barShown` the visible composer changes identity in one frame. Confidence **low** (from the code read,
`barShown` does not depend on the keyboard).

## 8. Instrumentation that discriminates

1. **Log every keyboard notification the plugin sees**: name, `frameBegin`, `frameEnd`,
   `animationDuration`, `isLocal`, plus `UIResponder.keyboardWillChangeFrameNotification` vs `WillHide`, in
   `willProcessKeyboardNotification` (`KeyboardManager.swift:86-89`) — the duration decides E1 vs "animated".
2. **Log every engine inset write**: subclass/instead swizzle `updateViewportMetricsWithInset:`
   (`FlutterViewController.mm:2312`) and print `CACurrentMediaTime()`, the value, and the caller
   (plugin vs `FlutterKeyboardInsetManager`): a single large step with no ramp = E1/E3; a ramp = animated.
3. **Per-frame geometry** (CADisplayLink at `.common`): `CACurrentMediaTime()`,
   `hostedAccessoryBar.frame`, `flutterView.keyboardLayoutGuide.layoutFrame`,
   `window.keyboardLayoutGuide`-equivalent, plus the keyboard's own window frame if reachable. Frame A vs B
   shows whether the *guide* jumped (N1) while the engine inset ramped, or both jumped together (E1).
4. **Target/inset trace on the engine side**: log `targetViewInsetBottom` and `physicalViewInsetBottom` at
   the head of `handleKeyboardNotification:` and in `startKeyBoardAnimation:` — confirms whether the
   `:66-69` dedupe swallowed the release (E2) and what start value the animation got.
5. **`keyboardAnimationVSyncClient` non-nil at release** — distinguishes E3 (compound branch) from a clean
   restart.
6. Repeat on iOS 16/17/18: `usesBottomSafeArea` (`CupertinoInteractiveKeyboardPlugin.swift:228-230`) only
   exists on 17+, and the engine's own interactive-keyboard tests are skipped on 17+
   (`FlutterTextInputPluginTest.mm:3617-3621`), so a UIKit-version-dependent guide behaviour is expected to
   differ.

## 9. Fix options (engine-side, if a route is confirmed)

* **E1**: the plugin can defend itself without engine changes by not letting the engine take the
  duration-0 `hideKeyboardImmediately` path — i.e. when the plugin is (or was) the inset driver and the
  keyboard is still on screen, write the live inset itself and keep `targetViewInsetBottom` on it, so the
  engine's dedupe (`:66-69`) swallows the notification instead of zeroing the inset. Cost: a few lines in
  `willProcessKeyboardNotification`; risk: it now owns the release in that corner.
  The real fix is upstream: `FlutterKeyboardInsetManager.mm:56-64` should not apply the "hide immediately"
  shortcut when a non-zero inset is currently applied and the view is visible.
* **E2**: after ignoring a notification, re-assert the inset with an animation to the *computed* value if the
  computed value differs from `physicalViewInsetBottom` — i.e. compare against the physical inset, not
  against the injected target. Cost: one condition at `:66-69`; this is the change that makes the plugin's
  target-injection hack unnecessary.
* **E3**: nil `_keyboardAnimationVSyncClient` *before* `removeAllAnimations` at `:270`, and retarget the
  running animation in the compound branch instead of only assigning the target (`:86-88`). Cost: 3-5 lines
  in the engine.
* **N1**: if the guide is what jumps, the bar must not be a pure constraint follower — either move it in a
  `CADisplayLink` from the keyboard's presentation geometry (what the plugin already does for the inset), or
  clamp its bottom to the live band the plugin measures. Cost: medium, and it duplicates the plugin's tracking.
