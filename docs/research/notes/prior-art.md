# Prior art: keeping a Flutter-rendered list glued to an interactively dismissed iOS keyboard

- Lane: prior art / decision support (question: what proven, ideally out-of-the-box techniques exist for this seam, and what do they tell us)
- Date: 2026-11-10
- Repo: cupertino_interactive_keyboard (Flutter 3.47.7, iOS only; bar = second Flutter engine pinned to a native container above the keyboard; main app = one engine; bar must stay a live Flutter widget; interactive feel must not change)
- Method: read-only. Sources fetched 2026-11-10. No builds, no runs, no device work.
- Written to: docs/research/notes/prior-art.md

## Bottom line

1. **No published package, plugin or Flutter issue solves this seam for a bar that lives in a second Flutter engine.** Prior art splits into two single-clock camps: (a) the bar is native and inside the keyboard (`native_keyboard_accessory`; `overlay_keeb`'s unpublished iOS path hosts a *second engine* inside `inputAccessoryView`), and (b) bar and list live in the *same* Flutter tree while UIKit owns the interactive dismissal (`interactive_keyboard_dismiss`, the only maintained package that tracks the drag). Nobody syncs two engines.
2. **The engine has no drag path at all.** During the interactive drag iOS posts frame changes with an empty frame; `FlutterKeyboardInsetManager` deliberately ignores them (E8), and animates the inset only from real notifications, sampled per vsync (E7). Any list that must move during the drag therefore depends on a value someone else writes (this repo: `updateViewportMetricsWithInset:`), exactly as the plugin already does.
3. **The known-hard part is the frame the value is read/written in, not the value.** The sharpest external source is react-native-keyboard-controller PR #412 (E5): a CADisplayLink callback that reads layer geometry is *always* one frame stale, and the merged production fix was to **predict the upcoming frame** rather than read the last one. This maps 1:1 onto this repo's bar, which lays itself out from the engine's inset on a CADisplayLink tick.
4. **The clipped-row + band artefact is a viewport-height artefact, and there is a prior-art layout that cannot produce it**: keep the list viewport at full height and move the *content* (`keyboard_attachable`'s FooterLayout pattern, `resizeToAvoidBottomInset: false`; E1). The cost is that bottom rows are covered instead of revealed.
5. **Frame cadence is a real but secondary variable.** Flutter iOS apps were hard-locked to 60 Hz until `CADisableMinimumFrameDurationOnPhone` (E11); the template sets it true and the engine's inset animator opts into the variable refresh rate explicitly (E7), while the plugin's tracking CADisplayLink sets no rate at all (`KeyboardManager.swift:232-234`). 120 Hz does not remove a frame of lag; it halves its duration (E10 #175790 still reports 3-4 frames of pipeline latency on a 120 Hz iPad).
6. **The residual gap after the keyboard is gone is a documented prior-art limitation, not a solved problem** (`interactive_keyboard_dismiss`: "a short gap under the input bar can be visible"; E4). Nobody claims frame-exact glue through the whole release.

**Read of the table:** every Flutter-rendered bar over an interactively dismissed keyboard is positioned from a *Dart-visible value* (viewInsets or a channel-reported height), never from the keyboard itself. The only mechanisms that are genuinely on the keyboard's clock are the two that put the bar into the keyboard's own view hierarchy as a native (or native-hosted) accessory. Nothing in the ecosystem keeps the *list* on that clock — even the maintained interactive-dismissal package accepts a catch-up tail.

**On "is Flutter 60fps by default?":** historically yes — Flutter iOS was restricted to 60 Hz until `CADisableMinimumFrameDurationOnPhone` was added to the template (2021/2022, E11). Today the template sets it true (`.../templates/app/ios.tmpl/Runner/Info.plist.tmpl:5-6`) and this repo's example does too (`example/ios/Runner/Info.plist:5-6`), so the app can render at ProMotion rates; the engine's keyboard animator explicitly requests the variable refresh rate and max refresh rate, while the plugin's tracking display link requests nothing. So the honest statement is: **the app is not locked to 60 Hz, but the bar's per-frame driver is unconfigured**; this is a "possible second-order contributor", not established as the cause.

## (4) Engine: the exact mechanism nobody else can see from Dart

- `FlutterKeyboardInsetManager.mm` (E7): `handleKeyboardNotification:` computes the inset, then animates a hidden zero-size view with `UIView.animateWithDuration`; the inset is sampled per vsync by a `FlutterVSyncClient` callback that reads the presentation layer (fallback: spring curve math) and calls `updateViewportMetricsWithInset:` (source lines ~249-382). The vsync callback is deliberately dispatched `dispatch_async(dispatch_get_main_queue())` with the comment "Make sure the new viewport metrics get sent after the begin frame event has processed" (line ~393) — the engine itself is doing frame budgeting here.
- `shouldIgnoreKeyboardNotification:` ignores an exactly-zero frame `UIKeyboardWillChangeFrameNotification` because "This happens when keyboard is dragged" (E8). Consequence: **during the drag the engine's animation is never started**, so the list gets no inset updates unless the plugin writes them.
- The private write path this repo uses exists on master: `FlutterViewController.mm` `-updateViewportMetricsWithInset:` sets `_viewportMetrics.physical_view_inset_bottom` then `updateViewportMetricsIfNeeded` (line 2263), `-physicalViewInsetBottom` (line 2268), `_keyboardInsetManager = [[FlutterKeyboardInsetManager alloc] ...]` (line 361) (E9).
- **Caveat:** the brief's pin `d8a2d6c768c334d53e16277f837970ffa1e2de81` returns 404 from both `flutter/engine` and `flutter/flutter`, so the engine citations above are `flutter/flutter` **master** today; the private-selector *names* match the plugin, which is the load-bearing fact, but exact-revision behaviour is not verified.

## What is ruled out (as prior-art answers — not as hypotheses about the root cause)

- **"An off-the-shelf package solves the second-engine bar + list seam."** Ruled out by the survey: no package puts a *live Flutter* bar on UIKit's clock on iOS except `overlay_keeb`'s unproven v0.0.1 iOS path; none addresses list sync across engines.
- **"The Flutter framework can do interactive dismissal out of the box."** Ruled out by #57609 and by the framework code: `ScrollView.keyboardDismissBehavior.onDrag` (`scroll_view.dart:540-552`) is a one-shot `unfocus()` on a scroll update, there is no `interactive` option, and the scroll physics never read a live keyboard position.
- **"Just use `flutter_keyboard_visibility`/`keyboard_dismiss`/`keyboard_actions`."** Visibility is a boolean (E: package table); `keyboard_dismiss` does not exist; `keyboard_actions` is a Dart overlay driven by viewInsets — the same seam, no live drag source. `/keyboard_accessory` likewise.
- **"60 Hz is the cause; enabling 120 Hz fixes it."** Ruled out as a root cause: the 60 Hz cap is gone in the template (E12), and #175790 still measures multi-frame latency at 120 Hz (E13). The unconfigured display link (E15) is a possible second-order factor only.
- **"The bar can stay a Flutter widget and be frame-locked if we write the inset fast enough."** Partly ruled out: the *inset* writes can be timely (pan handler before vsync, E16), but the *bar's* display-link read-back is one frame stale by construction (E5); the same-value coupling fixed the handoff, not the clock.
- **"CADisplayLink at 60 vs 120 is why the bar lags."** Not established: the link's rate is unconfigured (E15) but no source shows the link is throttled; this is a hypothesis to measure, not a conclusion.
- **"The clip band is cosmetic ListView overscroll/indicator."** Ruled out as an explanation for the *band between list and bar*: it only exists while a producer disagrees with the viewport edge; but plain viewport clipping is the *mechanism* by which the artefact renders (see idea 2), so it is not a separate bug to patch.

## The one critical evidence item

**E5 — react-native-keyboard-controller PR #412 (merged 2024-05-02).** It is the only external source that (a) names the exact failure mode this repo's current design is exposed to — "we read `layer` properties using `CADisplayLink` ... we'll always read a value for a previous frame. Thus we have always one frame delay" — and (b) reports that the *merged production fix* was not a faster read, not a different callback, but **predicting the value for the upcoming frame**, including the caveat that the prediction differs between simulator, device, and debugger-attached runs. Combined with the engine doxygen (E7/E8: the engine's own glue is a native per-frame animation and there is no drag path) and the repo's own trace (E10/E16: the bar reads `physicalViewInsetBottom` on a display-link tick), it says the seam is **frame bookkeeping around a shared value**, not a geometry or layout problem. If the owner fixes only one thing, it is *when the bar's value is sampled*, not what the value is.

## Confidence

- **High** that no out-of-the-box solution exists for the second-engine bar + list seam, and that the two proven families are (a) in-keyboard bar and (b) same-engine list with UIKit-owned dismissal. Multiple independent primary sources.
- **Medium-high** on the frame-staleness mechanism (E5/E7/E8/E15/E16 agree), because the repo's own traces are single-observer and my lane has no device access.
- **Medium** on how much of the *visible* artefact a frame-accounting fix would remove; the spec's addendum explicitly leaves pacing to a device run (E10), and no source measures a two-engine compositor's frame alignment.
- **Would flip it:** a device trace showing the bar's laid-out frame and the list's first row change landing in the same vsync (then the artefact is not the bar's read but the reserved-height/viewport mismatch, idea 2's territory), or a trace showing the display link ticking at half the keyboard's rate (then the unconfigured `preferredFrameRateRange` becomes the headline).

## Three "out of the box" ideas for this repo, ranked by fit

The constraints are respected: the bar stays a live Flutter widget in the second engine, the main app keeps one engine, the interactive feel is unchanged (the dismissal still belongs to UIKit), no plugin rewrite.

### 1. Predict the upcoming frame instead of reading the last one (RN #412 pattern) — best fit
*Do:* in the two places that consume a per-frame value — the bar's display-link layout from `physicalViewInsetBottom` (`KeyboardManager` today) and any inset write issued from a display-link tick — compute the value for the frame that is about to present (UIKit's presentation layer plus one `CADisplayLink.targetTimestamp` step, or the animation's start time/duration curve the engine already samples), and lay out/write that. Also give the tracking link an explicit `preferredFrameRateRange` matching the engine's (`FlutterDisplayLinkManager` sets `isVariableRefreshRateEnabled`/`maxRefreshRate`; the plugin sets nothing).
*Effect on the artefact:* removes the systematic ~1-frame (16.7 ms at 60 Hz, ~8.3 ms at 120 Hz) disagreement between the two producers — the visible band/half-row should shrink to anti-aliasing-level mismatch during a fast drag; it does **not** remove the catch-up after UIKit hides the keyboard.
*Risk:* prediction overshoot/oscillation at release and on spring keyboards; RN measured simulator-vs-device and debugger-attached differences. Small, surgical, testable in the existing trace.
*Why rank 1:* no architecture change, one value computation, directly targets the mechanism E5 documents, and the repo already owns the exact tick it needs to change.

### 2. Keep the list viewport full height and move the content (keyboard_attachable FooterLayout pattern) — best fit for the *clip* half
*Do:* app-side only: `resizeToAvoidBottomInset: false`, list stays at full height, and the visible bottom is produced by a padding/masking value fed from the same live inset (the value the plugin already publishes), so a row is never cut by a viewport edge that changes height one frame late. This is the same drawing model as `keyboard_attachable`'s `FooterLayout` + `resizeToAvoidBottomInset: false`.
*Effect:* the "row cut at the list viewport edge, background band, then composer" sequence cannot be produced by construction: there is no moving viewport edge; the worst case is rows occluded by the bar for a frame rather than a visible gap. It also removes per-frame Scaffold relayout, which is one candidate for dropped frames on long lists.
*Risk:* scroll-position semantics change (bottom rows are covered while the keyboard is up — the opposite of "reveal rows"), the app loses Scaffold's free inset handling for the composer, and it is not a fix for the frame lag: if the list still trails the bar by a frame, the artefact becomes occlusion instead of a gap. Doesn't touch the plugin, reversible.
*Why rank 2:* it fixes the half of the artefact that a frame fix cannot (the clip band has no reason to exist if nothing resizes), but it trades "reveal" for "cover", which is an app UX decision, not a plugin one.

### 3. Put the second engine's view inside the real `inputAccessoryView` (overlay_keeb iOS prior art; native_keyboard_accessory for the pure-native variant) — most native, highest cost
*Do:* instead of a pinned `CIKHostedAccessoryBar` container plus a display-link mirror, host the bar's `FlutterViewController` view as the accessory view (what `overlay_keeb`'s unreleased iOS source does: own `FlutterEngine` + `FlutterViewController` in an `inputAccessoryView`). UIKit then carries the bar with the keyboard on its own clock (`.interactiveWithAccessory` already in `CIKScrollView.swift:18`), so the bar cannot lag and needs no `physicalViewInsetBottom` read at all. The list keeps the inset write.
*Effect:* bar becomes frame-exact; the remaining visible mismatch is the list alone (which is the original owner complaint, E10 in the 2026-11-09 research note), so this alone would not finish the bug; combined with idea 1 or 2 it removes the bar as a producer.
*Risk:* accessory height becomes the keyboard's contract again — dynamic multiline composer growth (the spec's §2 problem), the app's reserved-height coupling, reparenting a Flutter VC's view into the keyboard's window (iOS 26's out-of-process keyboard makes host-view manipulation unreliable per E4's "iOS 26 ... keyboard is drawn outside the app's view hierarchy"), and the plugin owner already lists this as the long-term option, not now.
*Why rank 3:* it is the most native and the one the platform recommends, but it changes the height/ownership contract the 2026-11-10 spec just stabilized, and it still does not move the list.

One line for the owner: **rank order is "fix the clock (1), then remove the moving viewport edge (2), and only re-parent the bar into the keyboard (3) when the height contract is on the table."**
